github actions is a CI/CD platform, it allows your build, test, and deployment pipeline. You can run scripts on actions such as push, pull requests etc. Such scripts can build and test the pull requests and deploy the changes to production. Actions goes beyond devops, when other events happens in your repos, such as automatically add the appropriate label to new issues. Github provides linux, window, and macOs virtual machines to run your workflows, or you can host your own self-hosted runners in your own data center or cloud infra. (by going to self-hosted runners in runners sections) What is CI & CD? CI -> continuous integration means people can make changes to the code and merge them in a central location, CI means committing code into shared repo frequently. CD -> using automation to deploy your application changes to PROD. For github to recongnize any action workflows in your repo, you must save the workflow files in a directory called ./github/workflows. Different pipelines: why different pipelines, build, test and deployment pipeline? Components of workflow: 1. Event: you can trigger workflow on event. event can be some specific activity, workflow can be triggered via REST API and also run on schedule. 2. Workflow: workflow contains one or more jobs which run in parallel or sequential order, each job runs in its own virtual machine or container. each job contains steps that either run a script or run an action(which is a reusable extension that can simplify your workflow). A workflow is an automated process that will run one or more jobs. Workflows are defined by a YAML file. workflow is triggered by some event. A repo can have multiple workflows. each running on different trigger. workflow can reference to another workflow. 3. Job: job is a collections of steps which run on the same runner, eachs step is either a shell script or an action. steps execute in order & run on same runner so they can share data. we can configure job dependencies; by default they run in parallel. If job has any dependencies it will wait for it to finish. 4. actions -> actions are set of predefined jobs or code which perform specific task in workflow (e.g. checking out git repo), this reduces repetitive code 5. runners: server on which your workflow runs, each workflow is executed on freshly provisioned VM. each runner can run a single job at a time. workflow must have following basic components: event to trigger it, one or more job which contains series of steps. following steps occur to trigger a workflow run: 1. an event occurs on your repo, the event has an associated commit SHA and Git Ref. 2. github searches for .github/workflows directory in the root of repo for workflow files to be present in the associated commit SHA or Git ref of the event. 3. A workflow run is triggered if the event matches the ON in the workflow file. when workflow runs github sets GITHUB_SHA (commit SHA) and GITHUB_REF (git Ref) enviroment vars in the runner ENV. variables: you can set the varialbes (usually contain reusable data) and they are interpolated in the workflow file can be used. variable can be set via env key in workflow file or via setting of github repo. varibles can be used only in the runner, means in the steps which are executing on some machine. you can't use it before runner is running. context: it is a information about workflows, vars, runner env, job and steps. each context is an object that contains properties which can be strings or other objects. context can be accessed via ${{context}}, check contexts carefully they can contain malacious code which might be executed in workflow file. When to use contexts: you can use conext atmost at any point in the workflow, including when default variables would be unavailable. expressions: you can use expression to evaluate some conditions, expression can be combinations of literal values, references to a context or functions. expressions are commonly used in If keyword, e.g. if ${{< expressoin > }} settting ENV variables: env: MY_ENV_VAR: ${{< expression > }} Resuable workflow configurations: we don't need to copy paste the workflow, instead if we have permission we can invoke another workflow from currently running workflow this avoids duplication the workflow which calls is called caller workflow and which is called is called "called" workflow. you can also view dependency graph to check UI of dependencies when you run a called workflows (which is in different repo) its contexts (all context vars) are made same as caller workflow. composite actions vs reusable workflows: both help us to avoid duplicate code. reusable workflow allows you to run the entire workflow (jobs and steps) but in composite actions combine multiple steps that you can then run within a single job just like actions 1. composite actions can't contain jobs, its just collection of steps run like single step. 2. in case of composite jobs only one log will be visible in logs, while in called workflows each step and job is logged. 3. composite actions run on the same machine as the workflow which they are part of. if you want to run some steps on different machine, create another workflow. 4. passing output to steps, in case of composite actions you can add steps before or after the composite action as they run in job steps. But the reusable workflows run on job level you can't add steps before or after those. Workflow templates: when referencing a workflow by commit SHA you can ensure that everyone is using a same workflow, on the other hand when referncing the workflow by branch or tag this can cause issues. YAML anchors & aliases - anchor (&) identifies a piece of content that you want to reuse, while alais repeats that content in another location. anchor is named template and alias is using that template. custom actions
